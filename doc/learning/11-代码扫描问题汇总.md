# 11 代码扫描问题汇总

> 本章汇总本次仓库级全量扫描发现的**事实性问题**：①数据一致性（注册 vs 脚本 vs 引用）；②框架层代码缺陷（libs/locallibs 与工具脚本）；③命名/规范问题。所有条目均来自代码/数据交叉核验（`tools/collect.py` 采集、`data/*.json` 快照），可复现。按严重度排序。

## 1. 数据一致性问题（套件注册 vs 实际脚本）

### 1.1 已注册但脚本不存在（41 例）

| 套件 | 缺失用例数 | 影响 |
|------|-----------:|------|
| secscanner | 40（`oe_test_secscanner_027` 等） | `mugen.sh -f secscanner` 执行时这些用例找不到脚本，直接失败/跳过 |
| kata-containers | 1（`oe_test_kata-containers`） | 同上 |

> 交叉核验方法：遍历 `testcases/` 全部 7629 个脚本，与 `suite2cases/` 注册名比对，统计注册但无脚本的用例。**修复**：补齐脚本或从套件 JSON 移除。

### 1.2 脚本存在但未注册（879 个孤儿脚本）

| 测试域 | 孤儿脚本数 |
|--------|-----------:|
| feature-test | 552 |
| cli-test | 231 |
| smoke-test | 36 |
| embedded-test | 27 |
| system-test | 26 |
| doc-test | 5 |
| security_test | 1 |
| testsuite | 1 |

**影响**：这些脚本不会被任何 `-f/-r/-a` 执行到（僵尸用例），其中包含**真实用例脚本**：
- `testcases/cli-test/gdisk/oe_test_sgdisk_change_partition_type_code.sh`（sgdisk 改分区类型码）等 3 个 gdisk 用例；
- `feature-test` 下 552 个脚本——绝大多数位于 `feature-test/epol/`（ePOL 第三方软件包集合，如 gala-gopher/atril/botan2 等），是**一整批含 run_test 但未注册的用例脚本**；pkgship 各子套件脚本均已注册在对应 `suite2cases/*.json`，不属于孤儿。孤儿口径为"脚本名不在任何注册用例名集合中"。

**修复**：逐个甄别——确属正式用例的在套件 JSON 补注册；废弃的删除；子套件新建的补充对应 `suite2cases/*.json`。

### 1.3 用例名重复（461 个名字重复 / 471 次额外引用）

- 全库唯一用例名 **6718** 个，其中 **461 个名字**在多套件重复（如 `oe_test_dsconf` 系列在 `389-ds-base` 与 `389-ds-base_1.4.3.20` 都注册）；
- 版本变体套件（`389-ds-base_1.4.3.20`、`criu_3.15/3.16`、`hwloc_1.11.9`）的重复是**合理的设计**（同名用例在不同版本套件各自独立），但非版本变体的跨套件重名需要甄别；
- 框架提供 `check_casename.py`（不区分大小写查重）供 CI/开发者使用。

### 1.4 冒烟套件大规模重叠

- `smoke`（274 用例）与 `smoke-basic-os`（319 用例）**重叠 261 个**；
- 两套件同跑 `-a` 时 261 个用例执行两遍。建议合并或在文档注明分工。

### 1.5 其他数据问题

- `driver_test` 目录存在但**无 suite2cases JSON**（驱动测试套件由 Excel 清单经 `driver_generate_json.py` 生成，当前未生成任何已提交 JSON）；
- 4 个套件在 suite2cases 中存在但 category 未归入正式域：`security_test`、`smoke`、`smoke-syscare`、`testsuite`（case_extract 中归为"?"，即未按 `testcases/<域>/` 二级目录归类）。

## 2. 框架层代码缺陷（libs/locallibs）

### 2.1 `common_lib_shell.sh`（python3 不可用时的降级实现，缺陷最多）

> 生产环境默认有 python3 走 `common_lib_python.sh`，降级路径仅兼容用；但缺陷仍需知晓，避免误导。

| # | 位置 | 缺陷 | 后果 |
|---|------|------|------|
| 1 | `DNF_INSTALL` | `if ! dnf -y install ${pkgs}` 判断失败却可能已部分安装；重复安装 | 包已装时可能重复装/误报 |
| 2 | `DNF_INSTALL` 取位置 | 使用废弃算术展开 `$[ "NODE"$node"_LOCATION" ]` 做间接引用 | 在算术上下文中 `NODE1_LOCATION` 被当作变量名求值（未定义→0），**无法完成间接变量引用**，`location` 恒为 0，`local` 分支永不命中（本地环境也误走远端分支）；且实际环境变量名是 `LOCALTION`（拼写错位），双错位 |
| 3 | `DNF_INSTALL` 回滚调用 | `ret=SSH_CMD ...` 缺 `$()` 命令替换 | `ret` 存的是字符串 `SSH_CMD` 而非命令结果 |
| 4 | `DNF_REMOVE` 判断 | `if [ ret -ne 0 ]` 比较字面量 `ret` | 恒为真/假，逻辑失效 |
| 5 | `IS_FREE_PORT` | `check=IS_FREE_PORT new_port` 缺 `$()` | `check` 存字面量，判断失效 |
| 6 | `GET_FREE_PORT` | `for i in seq 100`（无 `$(...)`） | 循环只执行 1 次而非 100 次，随机找端口能力退化；且 `echo $new_port` 受 0–255 退出码上限约束 |
| 7 | `REMOTE_REBOOT` | `REMOTE_REBOOT_WAIT $node $waitetime` **拼写错误**（应为 `$waittime`） | 等待时间参数恒为空，重启等待用默认值 |
| 8 | `SSH_CMD` 传参 | 多处未加引号变量 | 含空格参数被拆分 |
| 9 | `SSH_CMD` 命令校验 | 仅校验非空 | 特殊字符注入面 |

### 2.2 `write_conf.py`（配置环境）

- `NODE_ITEM` 字段名为 **`LOCALTION`**（源码注释自认 `# TODO: LOCALTION 应为 LOCATION`）；该拼写贯穿 `read_conf.py`/`write_conf.py`/`env.json`，改动需同步三处。

### 2.3 `qemu_ctl.py` / `combination` JSON（QEMU 控制）

- 参数名/JSON 键为 **`kernal_img_path`**（kernel 拼写错误，源码原文如此）；CLI 与组合 JSON（`combination/*.json`）共用，改键需同步三处（qemu_ctl.py 解析、qemu_ctl.sh 透传、6 个组合 JSON）。
- `combination.py` `--dir` 分支逻辑错位：`if os.path.exists(arge.file)`（第 501 行）检查的是 `arge.file` 而非 `arge.dir`——单独用 `-d <目录>` 时 `arge.file` 为 `None`，`os.path.exists(None)` 抛 `TypeError`，该分支实际不可用；且即使修正检查对象，`listdir` 后也未对文件排序（顺序不确定）。

### 2.4 `common_lib_shell.sh` 功能缺失

- `P_SSH_CMD` / `SFTP` / `TEST_NIC` / `TEST_DISK` 在降级实现中直接 `LOG_ERROR` + `exit 1`（**不可用占位**）；依赖这些 API 的用例在无 python3 环境**必然失败**。

### 2.5 `results_listener.sh` 依赖

- `rsync_logs` 依赖本机 `rsync` 命令，未安装时日志同步静默跳过（仅告警）。

## 3. 规范/质量问题

### 3.1 命名不一致

- 套件命名：域名 `cli-test` vs 目录 `security_test`（下划线）不一致；
- 环境字段：`LOCALTION`（错）vs `LOCATION`（对）；
- QEMU 键：`kernal_img_path`（错）vs `kernel_img_path`（对）。

### 3.2 文档与代码不同步风险

- `doc/测试用例检视规范.md` 要求"config_params 只放预加载、pre_test 只放预置"，但全库 226 个用例使用 config_params 的分布需人工抽检是否合规（本扫描未做语义级判断）。

### 3.3 版本变体命名建议

- 版本变体套件命名 `389-ds-base_1.4.3.20` 用下划线拼接版本号，与基线 `389-ds-base` 在排序/检索上容易混淆；检视规范建议的 `源码包名_version1.json` 结构（base 用例复用）已在多版本场景应用，但仓库内仍有直接复制用例的做法（重复名 1.3 节）。
