# 06 测试自动化总览

> 本章回答"**mugen 仓库究竟在测什么、怎么组织**"。基于 979 个测试套、7189 个注册用例的全量扫描结果，按 9 大测试域展开，并给出整体执行架构、规模统计与测试活动组织方式。所有数字来自 `suite2cases/`（979 个 JSON）与 `testcases/` 全量解析（详见 09 章附录与 `11 代码扫描问题汇总`）。

## 1. 规模全景（全量扫描统计）

## 2. 测试活动组织方式（核心认知）

mugen 的测试组织遵循"**域 → 套件 → 用例 → 测试点**"四级结构：

```
测试域(9) → 套件(979) → 用例(7189) → 测试点(@Desc + CHECK_RESULT 断言)
```

1. **一个套件对应一个被测对象**：绝大多数套件以软件包/组件命名（`389-ds-base`、`httpd`、`dnf`、`gdisk`...），套件目录下每个用例脚本测试该对象的一个方面；
2. **一个用例对应一个功能点**：用例名即测试点（`oe_test_dsconf_backend_01` = dsconf 命令 backend 子命令第 1 个场景）；用例体内通过多条 `CHECK_RESULT` 断言逐项验证；
3. **版本变体套件**：同一对象不同版本作为独立套件（`389-ds-base_1.4.3.20`、`criu_3.15`、`criu_3.16`、`hwloc_1.11.9`）——这是**兼容性/多版本测试**的主要形态；
4. **组合矩阵**：嵌入式用 `combination/*.json` 把多套件 × 多环境（QEMU 架构/板卡）组织成回归矩阵（详见 04 章）。

## 3. 各测试域详解

### 3.1 cli-test（863 套件 / 4316 用例）——主体域

- **定位**：openEuler 版本测试的主要资产，覆盖系统绝大多数软件包的命令行工具、服务、配置。
- **组织形式**：`testcases/cli-test/<包名>/`，每套件一个目录；套件内既有**命令级用例**（`oe_test_dsconf_backend_01`），也有**服务级用例**（`oe_test_service_dirsrv-snmp` = 服务的 systemd 启停/使能/状态测试，见 08 章深挖）。
- **内容分布**（详见 07 章）：包管理、网络、服务、数据库、虚拟化、安全、编程语言等全部分类均在此域。

### 3.2 smoke-test（34 套件 / 734 用例）——冒烟

- **定位**：安装/引导后最小集验证系统可用的冒烟测试。
- **典型套件**：`smoke-basic-os`（319 例）、`smoke-A-Tune`、`smoke-syscare`（1 例）、`smoke`（全量冒烟集合 274 例）。
- **发现**：`smoke`（274 例）与 `smoke-basic-os` 用例重叠 261 个（见 11 章）。

### 3.3 feature-test（31 套件 / 810 用例）——系统特性专项

- **定位**：对"跨组件"的系统级特性做专项验证，每特性一套件、用例多。
- **典型套件**：`pkgship`（软件包依赖查询平台）、`A-Tune`（自动调优）、`gazelle`（轻量级网络服务）、`atune`、`stratoVirt_user_guide`（用户指南配套）等。

### 3.4 system-test（28 套件 / 865 用例）——系统级/集成

- **定位**：涉及文件系统、多机集群、内核等**系统级行为**的测试。
- **典型套件**：`FS_*` 系列（FS_File/FS_FileSystem/FS_Device/FS_Directory/FS_IO/FS_Negative/FS_Docker/FS_iSula，文件系统全维度）、`corosync-qdevice`（3 机仲裁）、`distributed_file_test`（分布式文件）、`kernel`（内核）。

### 3.5 embedded-test（15 套件 / 231 用例）——嵌入式

- **定位**：openEuler Embedded 的镜像/组件验证，依托 QEMU 与真实板卡（raspi4）执行（见 04/05 章）。
- **典型套件**：`embedded_os_basic_test`（49 例基础命令）、`embedded_mcs_rpi4_test`、`embedded_tiny_image_test`（tiny 镜像）、`embedded_version_basic_tests`（LTP/POSIX 版本回归）。

### 3.6 doc-test（6 套件 / 160 用例）——文档配套

- **定位**：验证官方文档（如《管理员指南》）示例与配套软件是否按文档所述工作。
- **典型套件**：`admin_guide`（文档示例 1:1 转用例）、`app-devel-guide`。

### 3.7 security_test（1 套件 / 71 用例）——安全专题

- **定位**：访问控制、权限、加密、审计等安全主题。
- **组织形式**：`testcases/security_test/` 下按 **47 个主题目录**组织（如 `oe_test_AccessControl_01` 在 AccessControl 主题下），suite2cases 仅 1 个 JSON（`security_test.json`）把全部用例注册为 1 套件。

### 3.8 testsuite（1 套件 / 2 用例）——开发模板

- **定位**：新测试套开发脚手架，提供 shell/py/bash 三种用例模板（详见 10 章）。

### 3.9 driver_test（无注册 JSON）——驱动测试素材

- **定位**：网络/存储/加速器驱动的专项测试；素材以 Excel 清单维护，经 `driver_generate_json.py` 生成 `suite2cases/driver_*.json`（见 02 章与 10 章）。

## 4. 执行架构（一次测试怎么跑起来）

```mermaid
flowchart TD
    A[配置环境<br/>mugen.sh -c --ip --password] --> B[conf/env.json 节点数组]
    B --> C[load_conf 注入 NODE*_* 环境变量]
    C --> D{选择执行对象}
    D -->|单套件| E[mugen.sh -f 套件]
    D -->|单用例| F[mugen.sh -r 套件 用例]
    D -->|全量| G[mugen.sh -a]
    E/F/G --> H[exec_case 用例脚本]
    H --> I[预检 CHECK_ENV<br/>不满足→skipped 255]
    H --> J[main 三段式 config_params→pre_test→run_test<br/>EXIT 陷阱→post_test]
    J --> K[results/套件/succeed|failed|skipped/用例]
    K --> L[退出码 0=通过 / 255=跳过 / 其他=失败 / 143=超时]
```

## 5. 测试内容构成（工具使用全景，反映测试手法）

对 7189 个注册用例的静态抽取统计（用例级频次；41 个缺失脚本的用例无字段）：

| 手法/工具 | 用例数 | 说明 |
|----------|-------:|------|
| `CHECK_RESULT` 断言 | 6461 | 断言是用例验收核心，占 89.9% |
| `DNF_INSTALL` 装包 | 4958 | 测试依赖被测包/工具，先装后测（post_test 回滚） |
| SSH / P_SSH_CMD 远端 | 292 | 多节点/远端执行（集群、主备、嵌入式） |
| `EXECUTE_T` 自定义超时 | 123 | 用例覆盖默认 30m 超时（性能/长任务用例） |
| config_params 参数化 | 226 | 用配置文件参数化用例输入 |
| 含 post_test 清理 | 6737 | 94% 用例带环境清理（DNF_REMOVE/删临时文件） |
| 含 pre_test 准备 | 6586 | 92% 用例先准备环境 |

> 结论：**"先装包 → 准备 → 执行 → 断言 → 清理回滚"** 是 mugen 用例的黄金模板，新用例照此结构编写即可与全库风格一致（详见 10 章）。

## 6. 测试活动的时间维度

- **版本回归**：`combination/embedded_version_test_round_1~5.json` 表明嵌入式在版本迭代周期内对同一批镜像执行 5 轮回归矩阵；
- **多版本兼容**：`389-ds-base_1.4.3.20`、`criu_3.15/3.16`、`hwloc_1.11.9` 等"包名_版本号"套件，是对同一软件不同版本的兼容验证；
- **CI 上报**：`libs/results_listener.sh` 可把运行结果周期 POST 到监控平台 + rsync 日志（见 02 章）。
